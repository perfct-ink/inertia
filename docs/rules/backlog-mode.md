## Backlog Mode

Applies when the user says to work on the backlog. It adds an autonomous workflow on top of [backlog.md](backlog.md); where the two overlap, this file wins for how work is delivered (backlog.md's rules on task files still hold).

Don't stop to ask which task to take or to confirm scope. Work through the tasks in `docs/backlog/` one at a time, highest priority first (`p0` before `p1`, and so on), skipping tasks whose `depends_on` files are still in `docs/backlog/`:

- **Work from `main`.** `git fetch` and start each task from an up-to-date `main`. Don't stack work on someone else's branch.
- **Run every test before committing.** Before each commit, and before moving to the next task, run all the checks that can run: `npm run lint`, the frontend type-check and tests, the backend tests (`rails test`), any migration (`rails db:migrate`, then check `schema.rb`), and the Swift build/tests when `macos/` changed. Run the whole suites, not just the new tests, and fix failures before committing. If a check can't run (missing dependencies, no network, no database), say which in the commit message, the task's `Blocked` note and the feature doc's History, and keep the work on its `backlog/*` branch rather than `main`. Never report a check as passing that you didn't run.
- **Unverified work → document, branch, push, move on.** When work is finished but a check couldn't run, or you're blocked, don't wait and don't ask. Write down what is needed in the task's own file on the branch (a `Blocked` section: what's done, which checks didn't run, and exactly what someone must do to verify or unblock it, such as `npm install` then `npm run lint`, or `rails db:migrate` then diff `schema.rb`), add `branch:` frontmatter, commit on `backlog/<task-filename-without-extension>`, `git push -u origin` it, return to `main`, and continue with the next unblocked task right away.
- **Completed task → commit and push to `main`.** Implement it, add tests, update `docs/features/`, and remove the task file, all in one commit with a `git log`-style message. Then `git push origin main`. Pushing `main` deploys to production through Coolify's Auto Deploy, without waiting for CI, so only push a task you consider complete and whose checks you could run; say plainly in the commit message and your report which checks you couldn't run.
- **Incomplete task → branch, commit, push.** If you can't finish (a product or privacy call, a risky migration, new infrastructure, an account or secret, or a needed tool that isn't available), put the work so far on a branch named `backlog/<task-filename-without-extension>`, commit it, and `git push -u origin <branch>`. Don't push the partial work to `main`. Record what's done and what's blocking in that task's own file on the branch (a `Blocked` section, plus `branch:` frontmatter). Leave the task file in place on `main`.
- **Don't edit other tasks' files or any shared index** when recording a blocker.
- **Build the conservative version.** When a call is genuinely the user's, build the cautious option behind the blocker note rather than guessing silently, and document the choice in the feature doc.
- **Keep going until the user says stop.** After each task, immediately pick the next one; never end a turn with a summary and wait. Don't stop because checks can't run or a task is blocked: put that task on its `backlog/*` branch (see above) and move to the next. When every task is done or blocked, re-read `docs/backlog/` (including `depends_on` chains that your own work unblocked), then work branch-only on anything that remains. Stop only when the user says `stop backlog`, or when the file `docs/backlog/.stop` exists (check before starting each task; the user creates it with `touch`). Finish and commit the current task first, then stop. Don't pause between tasks to announce that you're moving on, ask permission, or send progress notes; just start the next task. Give the full per-task report (pushed to `main`, pushed on a branch with the blocker, or untested) only when the user stops.
- **Pull requests.** This machine's `gh` login may not belong to the repo's account, so don't count on opening PRs from a session. Every pushed `backlog/*` branch should end up with a PR: on a machine where `gh` is logged in to the right account, run `make backlog-prs`, which opens a PR for each `origin/backlog/*` branch that has none (title and body come from the branch's last commit message, so write that message as the PR description). List every branch you pushed in your report so none are missed.
- **Never deploy by any other route**, and never force-push `main`.

### Verify before trusting

Backlog and feature docs drift like any other doc. A "still unbuilt" note has turned out to be stale more than once because the fix had already shipped, and a checkmark can be wrong the other way. Check the code before believing either direction, and before deleting a task as already built.
