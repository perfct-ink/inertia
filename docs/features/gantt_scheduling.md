# Gantt scheduling

## What it does
The Gantt tab of a folder (`/folders/:id?view=gantt`) draws the folder's epics and dated tasks as bars on an axis you can zoom (the shared `components/Timeline.tsx`).

- **Grouping**: milestone, then initiative, then epic, then task, each level indented one step (`groupGanttRows`, `data/schedule.ts`). An epic nests under its initiative, else under its own milestone; an initiative under its milestone; a task under its epic, else under its own `milestone_id`. Milestones come first by target date (`compareByTargetDate`, shared with the roadmap lanes), then whatever has no milestone: initiatives, epics with no initiative, tasks with no epic. A parent that is not in the lists passed in, or an epic with no dates (which is not drawn), is treated as absent, so its children stay at the level above instead of nesting under a missing row. Tasks with no due date are skipped.
- **Group rows**: a milestone or initiative row is bold, drawn in a neutral bar (yellow or red when its health is at risk or off track), shows the milestone's or initiative's server rollup as its `done/total` count, and cannot be dragged. An initiative with both a start and target date keeps them; otherwise its bar spans the rows under it. A milestone has only a target date, so its bar spans the rows under it and reaches its target date. A group with nothing under it, or nothing to draw, gets no row (the Initiatives page is the exception, below). On a folder's Gantt only milestones and initiatives that have an epic or task in that folder appear, and their `done/total` counts cover the whole Space, not just the folder.
- **Milestones**: milestones in this folder with a target date appear as diamonds on a row above the bars, if inside the chart's month range (`milestoneMarkers`).
- **Today line**: a red line when today is inside the range.
- **Drag to reschedule**: drag a bar to move it, or its left or right edge to resize. Dates snap to whole days and are saved on release (`shiftedRange`). Task bars save `start_date` and `due_date`; epic bars save `start_date` and `target_date`.
- **Zoom**: Days, Weeks, Months (default), Quarters or Years. Months fit the page; the others size the chart by days (36 px per day, 14 weeks, 3 quarters, 1 year) and scroll sideways. Axis labels are clipped to the chart's range (`axisTicks`). Dragging snaps to a whole day at every zoom because it works from the chart's total days, not the labels.
- **Weekends**: a "Shade weekends" toggle (on by default) shades Saturday and Sunday runs at Days and Weeks zoom; at coarser zooms they are too narrow and are not drawn (`weekendSpans`). Weekends are shaded, not skipped, so bars keep true calendar length.
- **Dependencies**: arrows between task bars, a critical-path highlight, and an editor for links (see [task_dependencies.md](task_dependencies.md)).
- **Dependency mode**: a picker per folder. *Ignore* moves only the dragged task. *Block invalid dates* refuses a move that breaks a link touching that task and shows an error. *Shift dependent tasks* moves the tasks that wait on it, keeping their length: later, only as far as needed, when the task moves later; earlier, by the same amount, when the task moves earlier and they were sitting exactly on their link (a task with a gap before it is left where it is, and a pulled task never goes past what its other links allow). The browser works this out in `planReschedule` and the server applies the same rules on save (see below).

- **Export**: the Gantt toolbar has "Export PNG" and "Print or save as PDF". PNG draws the same rows as the chart (month header, labels indented by depth, bars with the done part filled, critical bars outlined, today's line) onto an off-screen canvas at twice the size, in the page's current light or dark colours, and downloads it as `<folder name> gantt.png` (a browser failure shows an error under the toolbar). The PDF button opens the browser print dialog with only the chart visible (choose "Save as PDF"). Layout is `ganttExportLayout` in `data/ganttExport.ts`; painting and download in `util/ganttCanvas.ts`; print in `util/printGantt.ts`. No new libraries.

- **Baselines**: "Save baseline" in the Gantt toolbar snapshots the planned start and due date of every dated task in the folder (subfolders and their documents included). Picking a baseline from the "Baseline" list draws each task's planned span as a thin bar at the bottom of its track, so planned and actual can be compared; "No baseline" hides them, and the x button deletes the chosen baseline. Later date changes never alter a baseline. Epic rows have no planned bar. Code: `Baseline`/`BaselineTask`, `BaselinesController`, `api/baselines.ts`, `data/baseline.ts`.

## API and models
- `baselines` (`workspace_id`, `folder_id`, `created_by_id`, `name`) and `baseline_tasks` (`baseline_id`, `task_id`, `start_date`, `due_date`); `GET/POST /api/v1/folders/:id/baselines` (POST `{ baseline: { name } }`), `DELETE /api/v1/baselines/:id`. `Folder#scheduled_tasks` is the task set shared with `GET /folders/:id/contents`.
- `folders.dependency_mode` (`none`/`strict`/`flexible`, default `none`), `Folder` enum `dependency_mode` (prefix `dependencies`), permitted in `FoldersController` and returned by `FolderBlueprint`.
- Rescheduling reuses `PATCH /api/v1/tasks/:id` and `PATCH /api/v1/epics/:id`.
- **Server enforcement (tasks only)**: `TasksController#update` saves through `Scheduling::TaskUpdate` (`backend/app/services/scheduling/task_update.rb`). When an update changes `start_date` or `due_date` of a task that has a due date, the mode of the folder the task sits in decides (`tasks.folder_id`, else its document's folder; no folder means ignore). *Ignore*: nothing extra. *Block*: if any link touching the task would end up broken the update is refused with `422 { errors: ["That would break the dependency of \"B\" on \"A\"."] }` and nothing is saved. *Shift*: the task and every task moved with it are saved in one transaction, and the response is the task plus `rescheduled`, the other tasks that moved (full task objects, empty when none). Edits that do not touch the dates are never checked. Epics are not covered.
- The rules live in the plain Ruby `Scheduling::DependencyPlanner` (no database; the same rules as `planReschedule` in `frontend/src/data/dependency.ts`, so change both together). It only reads the task's links and the tasks they reach (strict: links touching the task; shift: everything downstream of it plus the other links into those tasks).
- The Gantt still computes the plan in the browser (instant refusal in Block mode, and it sends the moved task plus the tasks it shifted). The server reaches the same dates, so the extra updates change nothing; a refusal from the server (for example the task's own folder is stricter than the folder being viewed) shows its message under the toolbar.

## Who can view and change
Everything is scoped to the current Space. Task and epic updates need the member role or above (`WorkspaceScoped`); I did not check any finer limits.

## Web entry points
- Folder page, Gantt tab: milestone > initiative > epic > task, draggable epic and task bars.
- Epics page and Initiatives page, Timeline tab (`components/PlanningTimeline.tsx`): the same four levels for the whole Space, read-only, with a diamond for every dated milestone in range. It loads epics, initiatives, milestones and tasks itself, so the List tab doesn't fetch every task. Only tasks under a listed epic are drawn (tasks with no epic belong to the folder Gantt and would bury the epics). The Epics page passes its initiative-filtered epics, so the filter also narrows the initiatives, milestones and tasks shown. The Initiatives page also keeps initiatives that have no epic yet; one without dates is named under the chart as not shown.
- The roadmap uses the same `Timeline` but keeps its own lanes (`roadmapLanes`) and is read-only.

## Known limits
- Server enforcement uses the mode of the folder a task sits in directly. A folder's Gantt also lists tasks from its sub-folders and applies the viewed folder's mode in the browser, so set the same mode on a sub-folder if edits made elsewhere should obey it too. A sub-folder that is stricter than the folder being viewed can refuse part of a multi-task shift.
- Pulling earlier only follows links that were exactly tight before the move. A gap (slack) between two tasks is never closed, and a successor of two predecessors stops at the later one.
- Changing a task's folder, status or other fields does not re-run the schedule; only date changes do. Tasks created with dates, epic dates and edits to the links themselves are not checked either.
The zoom and weekend choices are not remembered between visits. Weekends are not skipped, only shaded.

- Flexible mode only pushes tasks later, never earlier, and only reacts to Gantt drags, not edits made elsewhere.
- Mouse and touch only; there is no keyboard way to reschedule.
- Arrows and the today line do not follow a bar while it is being dragged.
- Milestone and initiative bars cannot be dragged; their dates are edited on the Milestones and Initiatives pages. A milestone bar is a roll-up, so it can run past the milestone's own target date when work under it does.
- A task whose epic has no dates sits under its own milestone (or at the top), not under that epic's initiative.
- The Epics and Initiatives timelines load every task in the Space and draw no dependency arrows.
