# Features with requirements docs

## What it does
A **feature** is an epic with a requirements document. Users see features; code, API and database keep `epic` (the way Spaces are `workspace` and Collections are `table`). There is one kind: every epic is a feature, and every feature has a document.
- **A feature is within a project.** It is made from a project and its requirements document lives in that project. "New feature" asks for a name and creates the feature, then opens its requirements document. It is on the Features page (`/epics`), in the project's Files toolbar in the sidebar, and next to the other New buttons (`CreateItem`). With a project open the feature and its document go in it; with none they go in the Personal Project (a project, made if the Space has none, like a new document's).
- **The document is required.** The server builds it in the same request, from the requirements template (Problem, Goals, User stories, Acceptance criteria, Out of scope, Tasks), titled like the feature, in the feature's folder (its project, when it was made in one: the open project, or the project a promoted idea belongs to), else in the Personal Project, which then becomes the feature's folder too, by the person who made the feature. Every way of making an epic does this, including the API. It can't be deleted on its own (422: "Delete the feature instead"), can't be taken off the feature, can't move to another Space, and goes when the feature is deleted. Deleting a feature (after a confirmation) deletes the document and the tasks written in it; tasks that were only assigned to the feature are kept.
- **Existing epics became features.** The data migration `GiveEpicsRequirementsDocuments` gave each epic without a document a blank one from the template (see Migration below), so nothing is left that isn't a feature.
- **Tasks are written in the document.** Checklist lines become Space tasks (`document_task_lines.md`), and a task made in a feature's document gets that feature as its epic, so the epic's counts include it. A line has a checkbox: ticking it marks the task done, and a status change elsewhere changes the tick.
- **Progress header.** The document shows the feature's name (a link to its plan), its status (Planned, Active, Done: no tasks or none done is planned, all done is done, otherwise active) and "x of y tasks done" with a bar. The progress is hidden until the feature has a task. It follows task changes without a reload, because task changes refresh the epics.
- **Tasks only.** The header's "Tasks only" toggle (and the toolbar's, which is the same state) folds the whole document down to its headings and task lines and back. For a feature the choice is remembered per person per feature in local storage, so it reopens the way it was left; other documents don't remember it. This whole-document toggle is the only collapse (Alex, 2026-11-09): there is no per-heading fold.
- **Features page.** The Epics page is now called Features: "New feature", a Requirements button on each card that opens the document, and a delete that asks first. Its link in the sidebar and rail is called Features.

### Features and the planning views
A feature with no tasks is just a feature (its document); once its document has tasks it is an epic in the planning views. The choice made here is the most conservative reading that keeps today's views working: **the planning views list every feature exactly as they listed epics before**. Nothing is hidden for having no tasks, because the epic plan page's picker and backlog pane are how tasks get put into an epic, and the migration turns every existing epic into a feature, many of them with tasks assigned (not written in a document) or with no tasks yet. A feature with no tasks already shows no progress or counts (the plan page's rollup, this header), and adds no tasks to the milestone, initiative and roadmap rollups (a milestone's epic count still includes it), so it reads as "just a feature" until it has tasks; "has tasks" means any task of the feature, written in its document or assigned to it. If Alex wants bare features out of the roadmap, Gantt and rollups, that is a filter on `tasks_count > 0` in those views; it is not built.

## API and models
- `epics.document_id` (nullable in the database, unique, foreign key to `documents` that nulls on delete). `Epic belongs_to :document`; `Document has_one :feature_epic` (`dependent: :nullify`). The nullable column keeps the previous release working against the new schema (rollbacks don't reverse migrations) and lets a feature outlive a document deleted with its folder.
- Migrations: `20261108010001_add_document_to_epics` adds the column; `20261108010002_give_epics_requirements_documents` is the data migration (below).
- `Epic` builds the document before validation on create (`RequirementsTemplate.content(title)` in `backend/app/services/requirements_template.rb`; the folder is the epic's own, else `Workspace#personal_project`, which the epic is then filed in); `creator` is set by `EpicsController` (otherwise the Space's creator). The document must be present on create, can't be removed later, and must be in the epic's Space. A feature whose document went with its folder keeps working with `document_id: null`.
- `Task` sets `epic_id` from the document's feature when a task is created with `document_id` and no epic.
- `Epic#destroy` destroys the document, which destroys its tasks.
- `EpicBlueprint` returns `document_id`. `POST /api/v1/epics` takes `folder_id` (or the `X-Project-Id` header).
- `DocumentsController#destroy` answers 422 for a requirements document. `SpaceTransfer` refuses to move one, or a folder holding one (`FEATURE_DOCUMENT`); a copy is an ordinary document.
- Frontend: `hooks/useNewFeature.ts` (create and open), `hooks/useTargetFolder.ts` (the folder or the Personal Project; `useNewDocument` uses it too), `hooks/useTasksOnly.ts`, `components/FeatureProgress.tsx`, `data/feature.ts` (`epicFeatureStatus`, the storage key and read/write helpers), `api/epics.ts`. Task mutations now also refresh the epics.

### Migration
`GiveEpicsRequirementsDocuments` (a data migration with its own frozen copy of the template and its own light models, so later code changes can't alter it):
- For every epic with `document_id` null it makes a blank requirements document from the template, titled like the epic, by the Space's creator, in the epic's folder; an epic with no folder is filed in the Space's Personal Project (an existing active one, else a new project folder under the Root), and its `folder_id` is set to it so the feature and its document agree. Epics, their dates, planning fields, tasks and `updated_at` are otherwise untouched.
- Safe to rerun: it only looks at epics whose `document_id` is null, locks each epic and checks again, and does one epic per transaction. A rerun finds nothing to do (and makes a document for a feature whose document was deleted with its folder). It prints how many documents and Personal Projects it made.
- `down` does nothing and the column stays: the documents are ordinary documents that may hold writing, and the previous release ignores the column, so rolling the app back needs no undo. The first migration's `down` removes the column.
- Before production (it writes production data): restore a backup into a scratch database, run it there and check it; see the task file `docs/backlog/features-with-requirements-docs.md`.

## Who can view and change
Anyone who can write in the Space makes, renames and deletes features, like epics. The requirements document follows the usual document rules, except for the deletion, move and removal rules above.

## Web entry points
`/epics` (Features), the project's Files toolbar (`file-manager/ProjectNav.tsx`), `CreateItem`, the document page header (`view/document/DocumentScreen.tsx`).

## Known limits
- The requirements template exists twice, in Ruby (new features and the migration's frozen copy) and in `data/documentTemplate.ts` (the "New Requirements Doc" button); keep the live two in step (`docs/backlog/single-source-document-templates.md`).
- Only the Features page and the sidebar names say "feature". The plan page, roadmap, Gantt, Hierarchy, kanban, quick add and the API still say "epic" (`docs/backlog/rename-epics-to-features-in-the-ui.md`).
- Document-based features (a document in a feature folder, `feature_hierarchy.md`) still exist next to these; the two ideas need reconciling (`docs/backlog/reconcile-folder-features-with-epic-features.md`).
- The database column is nullable, so a feature can lose its document when its folder is deleted (the migration, rerun, makes it a new one). Deleting a project folder with features in it leaves them without a document (the folder's documents go with it); the features stay.
- The API accepts a `folder_id` that is a plain folder outside any project; only the web app always files in a project. A task that is in the feature's document and assigned to another epic keeps that epic, and a task moved into the document later isn't re-assigned.
- Task-less features are not kept out of the planning views (see above).
