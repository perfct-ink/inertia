# Embedded task lists

## What it does
A document can hold a live **task list** or **Gantt** of the Space's tasks. The toolbar button "Embed live tasks" (clipboard icon, next to "Tasks only") inserts a block at the cursor. The block stores only what to show; the tasks are read from the Space each time it is drawn, so it is never a stale copy.
- **Heading and progress:** "Open tasks in this Space" (or "All tasks in Sprint 3", "Open tasks in Messages / Design", "In Progress tasks in Launch plan") and "3 of 8 done" with a progress bar. The progress counts every task in the scope, whatever the status filter hides.
- **List:** one row per task: a checkbox, the title, the status (name and colour follow the configurable statuses of the task's own folder) and the due date. Rows are in due-date order, tasks with no date last. **Edits in the list edit the task itself**, through the same task update call as a task line: ticking the checkbox sets the task to `done`, unticking sets it back to `todo`; the status dropdown sets any status; the due date field (a date picker) sets or clears the due date. Done tasks are struck through. In a read-only editor the status and due date are plain text and the checkbox is disabled.
- **Gantt:** a bar per dated task (a task with a due date but no start date is a one-day bar on its due date), the links between the shown tasks, and the driving path outlined in red. It is read-only: bars cannot be dragged and links cannot be drawn here (use a folder's Gantt tab). A line under the chart counts tasks with no due date, which have nothing to draw.
- **Settings** (the sliders button, only while editing): Show as (List or Gantt), Tasks from (Whole Space, This document, One folder, One sprint), the folder or sprint to use, and Status (Open tasks, All statuses, or one status). Open tasks, meaning every status but done, is the default, with the whole Space as the default scope. Choosing a folder or sprint scope opens the settings and asks for the choice before anything is fetched. "This document" lists the tasks of whichever document the embed sits in; no id is stored, so a copy of the document lists the copy's tasks.
- **Remove** (the X button, only while editing) takes the block out of the document. The node can also be selected and deleted like any block.
- **Live:** the list refetches every 30 seconds while the page is visible, and straight away after any task change made in the app (task lines in the document, the Tasks page, ...), because those invalidate the same `tasks` queries.
- **States:** "Loading tasks…", "No tasks match this filter." / "No tasks yet.", and a failed load shows the error text with a "Try again" button (the API client also raises its usual error notice). A failed tick shows the API client's error notice.
- **Tasks only** (the toolbar toggle) keeps embeds visible, like task lists.
- Mobile and themes: the settings, rows and header wrap at 375px; the two icon buttons are 40px square; the Gantt scrolls sideways inside its own box; colours come from the theme tokens, so it follows dark mode.

## Privacy: what is stored and what each reader sees
The document stores only the four settings below (view, scope, folder or sprint id, status filter): no task, title, count or name is written into the node, the collab document, the saved content, the static HTML or a share link's content (`GET /api/v1/shares/access`). The list is fetched when it is drawn, with the reader's own sign-in and active Space (`GET /api/v1/tasks` is scoped to the Space the reader belongs to, and a Space they do not belong to is a 404), so a person who cannot see a task never receives it, however the document got to them: someone without access gets an error or an empty list, not the tasks. Folder and sprint names in the heading also come from the reader's own Space data. Copying or moving a document into another Space carries only the settings; a folder or sprint id from the old Space matches nothing in the new one (see Known limits).

## API and models
No new endpoints, models or migrations. The embed calls what the app already has:
- `GET /api/v1/tasks` with `document_id`, `folder_id` or `sprint_id` (the scope); the status filter is applied in the browser, so every embed with the same scope shares one cached list. `folder_id` means tasks in that folder itself, directly or through its documents, not those in its subfolders.
- `PATCH /api/v1/tasks/:id` (`status`) from the checkbox; `GET /api/v1/task_dependencies` for the Gantt (only while it is shown); `GET /api/v1/sprints` (only for a sprint scope); `GET /api/v1/workspace` (folder and document names).
- Document node `taskEmbed` (`frontend/src/extensions/TaskEmbed.ts`): a block atom with attributes `view` (`list` | `gantt`, default `list`), `scope` (`space` | `document` | `folder` | `sprint`, default `space`), `scopeId` (folder or sprint id; null for the Space and for `document`, which uses the document the embed sits in) and `status` (`open` | `all` | a task status, default `open`). The static HTML is `<div data-type="taskEmbed" data-view data-scope data-scope-id data-status>Live task list</div>`; unknown values read back as the defaults.
- The node is mirrored in `collab-server/src/schema.ts` (without it a shared document containing an embed can't be saved). **Deploy the collab server with the frontend**: an older collab server does not know the `taskEmbed` node and would reject documents that contain one. Both ship from one push to `main` (see [docs/deployment.md](../deployment.md)); do not deploy the frontend alone.
- `frontend/src/api/base.ts` `useResourceList` takes two new options, `enabled` and `refetchInterval`, and `useTasks(filters, options)` passes them through.
- Frontend: `data/taskEmbed.ts` (defaults, normalizing, scope filters, headings, status filter, sorting, progress, folder/document names), `components/editors/TaskEmbedPanel.tsx` (+ `.scss`, the list, Gantt and settings), `components/editors/TaskEmbedView.tsx` (the node view), `extensions/TaskEmbed.ts` (the node) and the toolbar button in `view/document/DocumentScreen.tsx`. Shared helpers added for it: `dependenciesAmong` (`data/dependency.ts`), `ganttLinks` and a `critical` option on `flatTaskRows` (`data/schedule.ts`); the folder Gantt (`GanttPane.tsx`) now uses the first two instead of its own copies.

## Who can view and change
Anyone who can open the document sees the embed, and only the tasks the tasks endpoint returns to them for the active Space (see Privacy above). Anyone who can edit the document inserts, configures and removes embeds; those settings are part of the shared document, so collaborators see changes live. Ticking a task or changing its status or due date uses the normal task update call: members and above can; for a viewer the API refuses and the error notice shows (the screen does not check the role first, the same as task lines). A read-only editor (`isEditable` false) shows the list without the settings, Remove or enabled checkboxes.

## Known limits
- Read-only Gantt: no dragging dates, no drawing links. Dates change on the task or in a folder's Gantt.
- The status filter options use the built-in status names; a folder that renames a status still shows its own name on the rows, but the filter menu says "To Do", "In Progress"...
- A folder scope means that folder only, not its subfolders. There is no scope for a project, epic, milestone, initiative or assignee, and no custom field filter or grouping.
- The scope is fixed to the Space's task list as the tasks endpoint returns it (one request for the whole Space with the default scope), the same cost as the task lines already pay.
- The list reads the reader's active Space (the `X-Workspace-Id` header), the same as task lines. A document of another Space opened while a different Space is active lists the active Space's tasks for the "Whole Space" scope.
- Moving or copying a document into another Space keeps a folder or sprint scope's old id, which matches nothing there: the embed shows an empty list until someone picks a folder or sprint again (backlog: `reset-embedded-task-list-scope-on-space-transfer`). Nothing from the old Space is shown.
- Sorting is by due date only; there is no manual order, and a task ticked done leaves an "Open" list as soon as the list refetches.
- Embeds are not shown in the document outline, in exports or on a shared read-only page (`SharedScreen`); the static HTML is only a labelled placeholder.
- Editing from the list is the checkbox, status and due date; the title, assignee and other fields change on the task (a task line, the Tasks page or the task detail).
